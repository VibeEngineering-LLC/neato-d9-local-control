# Neato Gen4 — механизм активации и что с ним делать (реверс MyNeato 1.6.2, 2026-09-18)

Источник: декомпиляция APK `com.neatorobotics.android_myneato` 1.6.2 (jadx). Каждый факт — из кода/ресурсов.

## Куда обращается за активацией

- **Облако: `https://orbital.neatocloud.com`** — ресурс `orbital_endpoint` (`res/values/strings.xml`), плюс
  `orbital_endpoint_intent = orbital.neatocloud.com`. Realtime/push: `https://neatov3.firebaseio.com` (Firebase).
- Retrofit-класс `retrofit/service/base/OrbitalRetrofitAPI.java` строит клиент с `baseUrl(orbital_endpoint)`.

**Эндпоинты аккаунта/активации (`OrbitalAPI.java`):**
| Метод | Путь | Назначение |
|---|---|---|
| POST | `/vendors/neato/sessions` | вход `{email,password}` → `token`; далее заголовок `Authorization: Token <token>` (сессионный, не OAuth) |
| POST | `/vendors/neato/users` | регистрация пользователя |
| POST | `/users/verify`, `/vendors/neato/users/verify/resend` | верификация e-mail |
| GET | `/users/me/robots` | список привязанных роботов |
| PUT | `/users/robots/{robotId}/unlink` | отвязать робота |
| GET | `/robots/{robotId}/last_state`, `/robots/{robotId}/features` | состояние/возможности |

**Команды роботу (`OrbitalRobotAPI.java`):** все через `POST /vendors/{vendor}/robots/{robotSerialNumber}/messages`
(старт/стоп/док/зоны — телом сообщения). Робот забирает команды из облака; прямого LAN-канала команд нет.

## Как активируется НОВЫЙ робот (реконструкция)

1. Приложение логинится на `orbital.neatocloud.com` → сессионный токен.
2. По **BLE** (`bluetooth/BluetoothRobotLinkingService`, `EncryptionService` — RSA поверх онбординга) передаёт
   роботу Wi-Fi-креды + linking-данные.
3. Робот подключается к Wi-Fi и **сам идёт на `orbital.neatocloud.com`** — там регистрируется/активируется и
   привязывается к аккаунту.
4. Приложение видит его в `/users/me/robots`.

**«Please download Neato app» на новом D8 = робот застрял на шаге 3:** облако выключено 30.11.2025, регистрация
не проходит → робот навсегда «не активирован».

## Критический факт для обхода

- **Приложение НЕ пинит сертификат** (`grep certificatePinner` → 0; DNS-класс `OrbitalRetrofitAPI$build$client$1`
  = обычный `Dns.SYSTEM`, без хардкод-IP). → **fake-cloud для ПРИЛОЖЕНИЯ тривиален**: подменить DNS
  `orbital.neatocloud.com` на свой сервер + свой TLS-сертификат (user-CA в Android). Приложение заработает.
- **Робот пинит сертификат** (доказано сообществом: RobertSundling neato-botvac Discussion #18 — робот рвёт TLS
  `unknown_ca` при подмене облака). → его прямое обращение на orbital подделать по сети НЕЛЬЗЯ.
- **Весь барьер — pinning НА РОБОТЕ, не в приложении.** И активация, и локальное управление упираются только в это.

## Как с этим быть (по убыванию реалистичности, без вскрытия)

1. **Recovery-прошивка D8 через USB-C** (`official-manual-firmware-update.md`). Первый и главный шаг: проверить
   эмпирически, снимает ли переустановка прошивки требование активации (перевод в рабочее автономное состояние).
   Когда оператор подключит новый D8 — сперва определить MTP это или rainbow; методика применима только для MTP.
2. **Fake-orbital для приложения + реверс протокола вживую.** Поднять локальный `orbital.neatocloud.com`
   (DNS + self-signed CA в телефоне — приложение не пинит), пройти линковку и записать, что именно приложение
   шлёт и что ждёт от облака. Активацию РОБОТА это само не завершит (робот пинит), но даёт точный протокол —
   основу и для vacuula-стиля решения, и для проверки, достаточно ли роботу ответа «активирован».
   ⚠ Подмена DNS/свой сервер в сети роутера — зона MikroTik/RasPi5 (§12): на ПК локально можно (hosts + сервер),
   на уровне сети — писать промпт владельцу.
3. **Vacuula server** — по сути решает ровно pinning робота (их ноу-хау, вероятно однократный прошивочный трюк).
   Ждать релиза (рутина слежения активна).
4. **Обход pinning на самом роботе** (подмена доверенного CA в прошивке) — требует root/serial = пайка/вскрытие,
   оператор пока не готов. Закрыто.

## Узкое место для сервера-замены (подтверждено субагентом, `myneato-apk-re.md`)

APK раскрывает протокол **приложение↔облако** полностью (логин, `/users/me/robots`, команды через
`…/messages` телом `{"ability":"cleaning.start",...}`, опрос `state.show` каждые 6 с). Но протокол
**облако↔робот** (как сервер доставляет команду роботу — поллинг роботом, websocket, MQTT) в клиентском APK
ОТСУТСТВУЕТ и из него не выводится. Именно это — главная неизвестность для сервера-замены (vacuula): мало
повторить REST для приложения, надо ещё говорить с роботом так, как ждёт его прошивка, пройдя его cert-pinning.

**Вывод:** активация завязана на мёртвый `orbital.neatocloud.com` + cert-pinning на роботе. Сетью в обход не
пройти. Практичный план для нового D8 — recovery-прошивка (проверить, снимает ли активацию), параллельно fake-orbital
для снятия протокола приложения; полноценная замена облака — vacuula либо доступ к роботу.
