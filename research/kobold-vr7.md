# Kobold VR7 / Vorwerk API v2 — живое облако (единственная ниточка к рабочему управлению)

Источник: `jmzg93/koboldVR7Integration` (README прочитан через `gh api`, 2026-09-15). Прислан оператором
как «преемник Neato».

## Суть

Kobold — немецкий бренд роботов Vorwerk (той же материнской компании, что закрыла Neato). **Kobold VR7 —
актуальный living-продукт, его облако РАБОТАЕТ.** HA-интеграция управляет роботом через **официальный
Kobold API version 2**:
- команды: **start / pause / stop / return-to-base**;
- мониторинг: батарея, ошибки, доступные команды, состояние (cleaning/docked/idle);
- зональная (`kobold_vr7.clean_zone`, по UUID зон) и картовая (`kobold_vr7.clean_map`, по UUID карты) уборка;
- требует аккаунт Kobold и робот, настроенный через официальное приложение Kobold.

Репозиторий: https://github.com/jmzg93/koboldVR7Integration (и `koboldHAIntegration`).

## Почему это важно для нашего D9

Разведка ранее считала ВСЁ облако Vorwerk мёртвым — это неверно: мёртво облако **Neato**
(`orbital.neatocloud.com`, отключено 30.11.2025), а облако **Kobold/Vorwerk (API v2)** живо. Это
единственный известный путь к работающему сетевому управлению роботом Vorwerk в 2026.

## Ключевой открытый вопрос (НЕ проверено, не утверждать)

Примет ли облако Kobold/Vorwerk наш **Neato D9**?
- «За»: одна материнская инфраструктура; в pybotvac был отдельный `Vorwerk()` vendor и client_id MyKobold;
  D9 внутри — тот же Linux Gen4, что и у линейки Kobold; по BLE есть штатная характеристика `Linking`.
- «Против»: D9 прошит на `Environment=production` с эндпоинтом Neato (`orbital.neatocloud.com`), а не
  Kobold; аккаунт/приложение Kobold может не видеть Neato-модели; серийник/тип устройства могут
  отвергаться API v2.

## План проверки (следующий шаг этого вектора)

1. Изучить, как `koboldVR7Integration` / Kobold API v2 аутентифицируется (client_id, OAuth-эндпоинт,
   хост API) — по исходникам `custom_components/kobold_vr7/`.
2. Понять, чем робот привязывается к аккаунту: приложением Kobold по BLE (`Linking`-характеристика) или
   только через облако. Совпадает ли механизм с онбордингом D9.
3. Проверить фактом: можно ли Neato D9 залинковать в аккаунт Kobold/MyKobold и увидеть его в API v2.
   Если да — команды уборки становятся доступны через живое облако.
4. Если облако Kobold отвергает Neato-устройства — это финальный тупик для сетевого управления;
   остаётся только аппаратный вектор (`serial-hardware-vector.md`).

## Связь с другими векторами

- BLE (`ble-vector.md`): характеристика `Linking` — штатный механизм привязки, пригодится, если Kobold-облако примет D9.
- WiFi (`wifi-cloud-deadend.md`): мёртв именно эндпоинт Neato; Kobold — отдельный, живой.
